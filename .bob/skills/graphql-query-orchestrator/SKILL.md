# Query Orchestrator Skill

## Purpose
Extend parent GraphQL types with child resource fields using StepZen materializers, creating unified queries that fetch related data in parallel. This optimizes GraphQL APIs for agentic AI use cases by reducing the number of separate queries needed.

## Key Concept
Instead of creating separate composite types, **extend the parent type** returned by the base query with additional fields that use `@materializer` to fetch related data. The orchestrated query calls the parent REST endpoint and returns the parent type, which is then extended with child resource fields.

## Critical Requirements (Must-Have)

These requirements are **non-negotiable** for materializers to work correctly:

1. ✅ **Base queries MUST have `configuration: "upstream_configuration"`**
   - Required for materializers to inherit API configuration
   - Without this, materializers cannot access authentication context
   - **See `graphql-security` skill for authentication configuration**

2. ✅ **Base queries MUST have authentication via `headers` OR `forwardheaders`**
   - Required for materializers to inherit authentication
   - Materializers automatically inherit from referenced queries
   - **See `graphql-security` skill for authentication methods**

3. ✅ **Orchestrated query MUST call parent REST endpoint**
   - Use `@rest` directive identical to the base parent query
   - Must return the parent type (e.g., `Customer`), not a composite type

4. ✅ **Orchestrated query MUST return parent type**
   - Return the parent resource type (e.g., `Customer`)
   - Do NOT create a new composite type (e.g., `CustomerDetails`)

5. ✅ **Materializers reference base queries by name**
   - Use `query: "getCustomerAddresses"` to reference the base query
   - Materializers automatically inherit `configuration` and authentication from referenced queries
   - **Never add `configuration` to `@materializer` directive** (not supported)

## When to Use This Skill

Use query orchestration when:
- Parent resource has **2 or more child endpoints** (e.g., `/accounts/{id}/compliance`, `/accounts/{id}/bankdetails`)
- Agent needs **complete entity data in a single query**
- Child resources **share the same parent ID parameter**
- You want to **reduce API calls** and improve performance

## When NOT to Use

Do not use query orchestration when:
- Only **1 child endpoint** exists (not worth the complexity)
- Child resources require **different authentication** methods
- Parent and child have **no ID relationship**
- Child resources are **optional** and rarely needed

## Implementation Pattern

### Step 1: Ensure Base Queries Have Required Configuration

**All base queries must have `configuration` and `headers`:**

```graphql
type Query {
  # Parent query - MUST have configuration and headers
  getCustomer(customerId: ID!): Customer
    @rest(
      endpoint: "https://api.example.com/customers/$customerId"
      method: GET
      configuration: "upstream_configuration"  # ✅ Required
      headers: [                                # ✅ Required
        { name: "Authorization", value: "Bearer $upstream_api_token" }
      ]
    )
  
  # Child query - MUST have configuration and headers
  getCustomerAddresses(customerId: ID!): [Address]
    @rest(
      endpoint: "https://api.example.com/customers/$customerId/addresses"
      method: GET
      configuration: "upstream_configuration"  # ✅ Required
      headers: [                                # ✅ Required
        { name: "Authorization", value: "Bearer $upstream_api_token" }
      ]
    )
  
  # Another child query - MUST have configuration and headers
  getCustomerBankDetails(customerId: ID!): BankDetails
    @rest(
      endpoint: "https://api.example.com/customers/$customerId/bankdetails"
      method: GET
      configuration: "upstream_configuration"  # ✅ Required
      headers: [                                # ✅ Required
        { name: "Authorization", value: "Bearer $upstream_api_token" }
      ]
    )
}
```

### Step 2: Create Orchestrated Query (Identical to Parent Query)

**The orchestrated query must be identical to the parent query:**

```graphql
type Query {
  # ... base queries above ...
  
  # Orchestrated query - identical to getCustomer
  getCustomerDetails(customerId: ID!): Customer  # ✅ Returns parent type
    @rest(
      endpoint: "https://api.example.com/customers/$customerId"  # ✅ Same endpoint
      method: GET
      configuration: "upstream_configuration"  # ✅ Same configuration
      headers: [                                # ✅ Same headers
        { name: "Authorization", value: "Bearer $upstream_api_token" }
      ]
    )
}
```

### Step 3: Extend Parent Type with Materializers

**Extend the parent type (not create a new type):**

```graphql
type Customer {
  # Original fields from parent endpoint
  id: ID!
  name: String
  email: String
  
  # Extended fields using materializers
  # Materializers automatically inherit configuration and headers from referenced queries
  addresses: [Address]
    @materializer(
      query: "getCustomerAddresses"              # ✅ References base query
      arguments: [{ name: "customerId", field: "id" }]  # ✅ Extracts ID from parent
    )
  
  bankDetails: BankDetails
    @materializer(
      query: "getCustomerBankDetails"
      arguments: [{ name: "customerId", field: "id" }]
    )
  
  orders: [Order]
    @materializer(
      query: "getCustomerOrders"
      arguments: [{ name: "customerId", field: "id" }]
    )
}
```

## How It Works

1. **Client calls orchestrated query**: `getCustomerDetails(customerId: "123")`
2. **Orchestrated query fetches parent**: Calls `GET /customers/123`
3. **Returns parent object**: `{ id: "123", name: "John", email: "john@example.com" }`
4. **Materializers execute in parallel**:
   - Extract `id: "123"` from parent object
   - Call referenced base queries with extracted ID
   - Base queries provide `configuration` and `headers` context
   - Materializers inherit authentication automatically
5. **Result is unified object**: All data combined in single response

## Workflow

### Step 0: Environment Setup (check first)

Before any work, verify that environment variables are loaded. See **README.md** for instructions on running `set-env.py`.

### Step 1: Analyze Schema
1. Identify the input filename from the `input/` directory (e.g., `iwhi-graphql-account-input.json`)
2. Extract base name without extension (e.g., `iwhi-graphql-account-input`)
3. Read `api-connect/graphql/schema/{input-filename}.graphql` (e.g., `schema/iwhi-graphql-account-input.graphql`)
4. Parse all Query type operations
5. Identify parent-child relationships:
   - Path patterns: `/resource/{id}` vs `/resource/{id}/subresource`
   - Naming conventions: `getCustomer` vs `getCustomerAddresses`
   - Parameter matching: shared ID parameters

### Step 2: Group Related Operations
1. Find operations sharing the same parent ID parameter
2. Group by parent resource type
3. Create list of candidate operations for merging

### Step 3: Interactive Confirmation - Operation Name

**STOP and wait for user confirmation before generating any files.** Do not write or modify any `.graphql` file until the user has explicitly confirmed the proposed orchestration and operation name.

Present proposed merge to user:
```
Found related operations for Customer:
- getCustomer(customerId)
- getCustomerAddresses(customerId)
- getCustomerBankDetails(customerId)

Proposed merged operation: "getCustomerDetails"

Options:
1. Accept "getCustomerDetails"
2. Suggest a different name
3. Skip this merge
```

**Enforcement:** If no confirmation has been received yet, the very next action MUST be to present this prompt and wait. Writing any `.graphql` file before the user responds is a violation of this skill.

### Step 4: Update Tool Configuration for Orchestrated Query

**Important**: Only the orchestrated query needs tool configuration updates. All queries that are part of the orchestration (parent + children) should have their tool definitions removed. Non-orchestrated queries keep their existing tool definitions unchanged.

**Rules:**
1. **Add tool definition for the new orchestrated query only**
2. **Remove tool definitions for the parent query** (e.g., getAccountByID - now replaced by orchestrated query)
3. **Remove tool definitions for all child queries** (e.g., getComplianceInfoForID, getBankAccountForID, getCreditWorthinessForID)
4. **Keep tool definitions for non-orchestrated queries unchanged** (e.g., searchAccountsByName)
5. **Update visibility configuration** to include the orchestrated query and exclude all orchestrated queries (parent + children)

**Example:**

Before orchestration:
```graphql
# tools/{input-filename}.graphql
extend schema @tool(name: "getAccountByID", ...)           # Parent - REMOVE (replaced by orchestrated)
extend schema @tool(name: "searchAccountsByName", ...)     # Non-orchestrated - KEEP as-is
extend schema @tool(name: "getComplianceInfoForID", ...)   # Child - REMOVE (part of orchestrated)
extend schema @tool(name: "getBankAccountForID", ...)      # Child - REMOVE (part of orchestrated)
extend schema @tool(name: "getCreditWorthinessForID", ...) # Child - REMOVE (part of orchestrated)
```

After orchestration:
```graphql
# tools/{input-filename}.graphql
extend schema @tool(name: "getAccountData", ...)           # New orchestrated query - ADD
extend schema @tool(name: "searchAccountsByName", ...)     # Non-orchestrated - UNCHANGED
```

**Visibility update:**
```graphql
# Before
fields: "(getAccountByID|searchAccountsByName|getComplianceInfoForID|getBankAccountForID|getCreditWorthinessForID)"

# After - only orchestrated and non-orchestrated queries
fields: "(getAccountData|searchAccountsByName)"
```

### Step 5: Generate Merged Schema
1. Verify all base queries have `configuration` and `headers`
2. Create orchestrated query (identical to parent query)
3. Extend parent type with materializer fields
4. Preserve original operations for backward compatibility
5. **Check for duplicate type names across all schema files** - Scan `api-connect/graphql/schema/` for existing type definitions
6. **Resolve type name conflicts** - Use unique names, extend existing types, or unify types as appropriate

### Step 5.1: Handling Duplicate Types Across Multiple APIs

For the full resolution strategy (Option A: unique names / Option B: extend type / Option C: unify), including examples and the automatic conflict detection process, see **`graphql-api-creator` skill Section 11.2**.

Key rule: GraphQL schemas cannot have duplicate type definitions. Always scan `api-connect/graphql/schema/*.graphql` for existing type names before generating new types. When in doubt, use unique type names.

### Step 6: Validate and Deploy
1. Validate schema syntax
2. **Check for duplicate type definitions** - Ensure no types are defined multiple times
3. Test orchestrated query
4. Verify materializers execute correctly
5. Confirm authentication works for all child queries
6. **Verify type extensions work correctly** - Test that extended types include all fields from base and extended definitions

## Troubleshooting

### Issue: Deployment fails due to non-ASCII characters in comments

See `graphql-api-creator` skill Issue 8 for the full description and fix. In short: never write any character above U+007F in generated `.graphql` files — replace em-dash, en-dash, smart quotes, ellipsis with plain ASCII equivalents.

### Issue: Orchestrated query returns null

**Cause**: Orchestrated query doesn't call a REST endpoint

**Solution**: Add `@rest` directive to orchestrated query, calling the parent resource endpoint (identical to base parent query)

### Issue: Sub-queries receive null parameters

**Cause**: Field name mismatch in materializer arguments

**Solution**: Ensure `field: "id"` matches the actual ID field name in the parent type

### Issue: Authentication fails on sub-queries (HTTP 401/500)

**Cause**: Base queries missing `configuration` or authentication parameters

**Solution**:
1. ✅ Verify ALL base queries have `configuration: "upstream_configuration"`
2. ✅ Verify ALL base queries have `headers` OR `forwardheaders` for authentication
3. ✅ Materializers automatically inherit these from referenced queries
4. ❌ Do NOT add `configuration` to `@materializer` directive (not supported)

**For detailed authentication troubleshooting, see the `graphql-security` skill.**

### Issue: Type mismatch errors during deployment

**Cause**: Orchestrated query returns wrong type (composite type instead of parent type)

**Solution**: Orchestrated query should return the parent type (e.g., `Customer`), then extend it with materializers

### Issue: Some materializers don't execute

**Cause**: Syntax error or missing query reference

**Solution**: Verify all referenced queries exist and are spelled correctly

### Issue: Materializers work locally but fail in production

**Cause**: Environment variables not configured in deployment

**Solution**:
1. Verify environment variables are set in production
2. Check `config.yaml` references correct variable names
3. Ensure variables are accessible to GraphQL runtime

### Issue: Deployment fails with "field Query.X is already defined"

**Cause**: Incorrect tool definition format in `tools/index.graphql`

**Solution**:
1. ✅ Use `extend schema` with `@tool` directives
2. ❌ Do NOT use `extend type Query` with field redefinitions
3. The `@tool` directive should reference existing queries, not redefine them

**Correct:**
```graphql
extend schema
  @tool(
    name: "getAccountInsights"
    description: "..."
    graphql: { expose: true, types: "Query", fields: "getAccountInsights" }
  )
```

**Incorrect:**
```graphql
extend type Query {
  getAccountInsights(accountID: String!): AccountData
    @tool(description: "...")
}
```

## Files Modified

- `api-connect/graphql/schema/{input-filename}.graphql` - Add orchestrated operations and extend parent types (where {input-filename} is the base name from the input file)
- `api-connect/graphql/tools/{input-filename}.graphql` - Update tool exposure based on user selection (where {input-filename} is the base name from the input file)
- `api-connect/graphql/index.graphql` - Update visibility configuration to match tool-exposed queries

**Example:** For input file `iwhi-graphql-account-input.json`:
- Modify: `schema/iwhi-graphql-account-input.graphql`
- Modify: `tools/iwhi-graphql-account-input.graphql`
- Modify: `index.graphql`

### Updating Visibility Configuration

After updating tool exposure in `tools/{input-filename}.graphql`, you must update the visibility configuration in `index.graphql` to match.

**Pattern:**
```graphql
schema
  @sdl(
    files: [
      "schema/{input-filename}.graphql"
      "tools/{input-filename}.graphql"
    ]
    visibility: {
      expose: true
      types: "Query"
      fields: "(query1|query2|query3)"
    }
  )
  {
    query: Query
  }
```

**Example for input file `iwhi-graphql-account-input.json`:**
```graphql
schema
  @sdl(
    files: [
      "schema/iwhi-graphql-account-input.graphql"
      "tools/iwhi-graphql-account-input.graphql"
    ]
    visibility: {
      expose: true
      types: "Query"
      fields: "(getAccountByID|getAccountInsights)"
    }
  )
  {
    query: Query
  }
```

**Rules:**
1. Extract field names from all `@tool` definitions in `tools/{input-filename}.graphql`
2. Build regex alternation pattern: `"(field1|field2|field3)"`
3. Only queries with `@tool` definitions will be visible in public API
4. Queries without `@tool` definitions are hidden but available for internal use (e.g., materializers)

**Example:**

If you expose only the orchestrated query:
```graphql
# tools/{input-filename}.graphql
extend schema
  @tool(
    name: "getCustomerDetails"
    description: "..."
    graphql: { expose: true, types: "Query", fields: "getCustomerDetails" }
  )
```

Then update visibility:
```graphql
# index.graphql
visibility: {
  expose: true
  types: "Query"
  fields: "(getCustomerDetails)"
}
```

If you expose all operations:
```graphql
# tools/{input-filename}.graphql
extend schema @tool(name: "getCustomer", ...)
extend schema @tool(name: "getCustomerAddresses", ...)
extend schema @tool(name: "getCustomerDetails", ...)
```

Then update visibility:
```graphql
# index.graphql
visibility: {
  expose: true
  types: "Query"
  fields: "(getCustomer|getCustomerAddresses|getCustomerDetails)"
}
```

## Best Practices

1. **Always verify base queries have configuration and authentication** before creating materializers (see `graphql-security` skill)
2. **Keep orchestrated query identical to parent query** - same endpoint, same configuration
3. **Return parent type, not composite type** - extend the parent type instead
4. **Test authentication thoroughly** - verify materializers inherit authentication correctly (see `graphql-security` skill)
5. **Preserve original operations** - for backward compatibility and flexibility
6. **Only expose orchestrated query as tool** - remove tool definitions for parent and all child queries, keep non-orchestrated queries unchanged
7. **Use correct tool format** - `extend schema` with `@tool`, never `extend type Query` with field redefinitions
8. **Document orchestrated operations** - explain what data they fetch
9. **Use descriptive names** - make it clear what the orchestrated query does
10. **Check for duplicate type names** - scan all existing schema files before generating new types
11. **Resolve type conflicts appropriately** - use unique names for different types, `extend type` for adding fields, or unify identical types
12. **Test deployment** - verify no "field already defined" or "type already defined" errors before considering task complete
13. **Never display literal secrets in chat** - obfuscate API keys, tokens, and credentials per the rule in Section 0 before showing them to the user
